## 2. How To Think About AI-200

The exam is trying to validate a developer who can translate a requirement into an Azure implementation and then operate it.

Use this reasoning sequence:

1. **Classify the workload.** Synchronous request, durable command, notification event, background job, vector retrieval, cache lookup, or telemetry?
2. **Find the non-negotiable constraint.** Kubernetes control, scale-to-zero, ordered/durable messaging, fan-out, relational joins, document partitioning, submillisecond in-memory access, exact vector recall, or secretless authentication?
3. **Choose the service boundary.** Compute, data, integration, configuration, and observability are separate decisions.
4. **Choose the documented behavior.** Delivery mode, consistency, index, replica floor, revision mode, lock settlement, or refresh strategy often decides the answer.
5. **Secure the data path.** Prefer workload identity or managed identity plus the least-privileged data-plane role; do not confuse authentication with authorization.
6. **Plan failure handling.** Retries require idempotency. Messages need settlement and dead-letter handling. Caches can be stale. Distributed calls need correlated traces.
7. **Prove the diagnosis.** Use the signal that answers the question: metrics for trends, logs for detailed records, traces for causal request flow, Kubernetes events for scheduling/runtime state.

### A compact question-solving loop

> Requirement → constraint → service → configuration → failure mode → observable evidence

Plausible distractors usually satisfy the broad requirement. The correct option also satisfies the constraint. For example, both Event Grid and Service Bus move information, but an event notification and a durable work command have different semantics.

## 4. Architecture Mental Model

~~~mermaid
flowchart LR
    C[Client] --> API[Container App, App Service,\nAKS workload, or Function]
    API --> COSMOS[Cosmos DB for NoSQL\nJSON + vector data]
    API --> PG[Azure Database for PostgreSQL\nrelational + vector data]
    API --> REDIS[Azure Managed Redis\ncache + vector index]
    API --> SB[Service Bus\ndurable commands/messages]
    API --> EG[Event Grid\nevent notifications]
    SB --> WORKER[Container or Function worker]
    EG --> HANDLER[Function or HTTP handler]
    API -. identity .-> KV[Key Vault\nsecrets]
    API -. configuration .-> AC[App Configuration\nsettings and Key Vault references]
    API -. telemetry .-> OTEL[OpenTelemetry]
    WORKER -. telemetry .-> OTEL
    HANDLER -. telemetry .-> OTEL
    OTEL --> MON[Azure Monitor / Application Insights\nmetrics, logs, traces]
~~~

This is a menu, not a requirement to deploy every service:

- **Container Registry** owns deployable image artifacts.
- **App Service** hosts a web/API container with a managed web platform.
- **Container Apps** hosts revisioned, microservice-style or event-scaled containers without exposing Kubernetes operations.
- **AKS** is the choice when Kubernetes manifests and cluster-level control are requirements.
- **Functions** supplies trigger-oriented serverless execution.
- **Cosmos DB for NoSQL** co-locates schemaless items and vectors and scales by logical partition.
- **PostgreSQL** supplies relational modeling, SQL, joins, and vector extensions.
- **Managed Redis** supplies in-memory caching and vector retrieval where latency and cache semantics dominate.
- **Service Bus** carries durable work and business messages; **Event Grid** distributes facts that something happened.
- **Key Vault** holds secrets; **App Configuration** centralizes non-secret settings and references secrets.
- **OpenTelemetry** propagates context; Application Insights and Azure Monitor let you correlate, query, and visualize it.

# DOMAIN 1 — Develop containerized solutions on Azure

**Weight: 20–25%**

## 1.1 Implement container application hosting

### What Microsoft expects

You must be able to create and manage images in Azure Container Registry (ACR), run registry-side builds with ACR Tasks, and deploy/configure a custom container in Azure App Service.

### 1.1.1 Build, store, version, and manage images in ACR

**Core concepts**

- A repository is a named collection of related images; a tag is a mutable label; a digest identifies immutable image content.
- Production deployments need traceability. Use a unique version or commit-derived tag, and preferably deploy by digest where operationally suitable.
- A familiar tag such as <code>latest</code> can move. Microsoft advises stable tags for base-image maintenance scenarios, but unique tags or digests for deployment traceability.
- Registry authentication and image-pull authorization are separate from image naming. Grant the runtime identity the minimum pull permission.

**Implementation / CLI**

~~~bash
# Build locally, tag, and push
az acr login --name myregistry
docker build -t myregistry.azurecr.io/ai-api:2026.09.07 .
docker push myregistry.azurecr.io/ai-api:2026.09.07

# Inspect artifacts
az acr repository list --name myregistry --output table
az acr repository show-tags --name myregistry --repository ai-api --orderby time_desc
~~~

**When to use it:** Use ACR as the private Azure image source for App Service, Container Apps, or AKS.

**How to choose:** If the question asks for a build without a local Docker daemon, choose ACR Tasks rather than a local <code>docker build</code>. If it asks for a reproducible deployment, choose a unique tag or digest rather than a moving tag.

### Exam Trap

An image tag is not the image identity. Reusing a tag can make deployments non-reproducible even though the repository name looks correct.

### 1.1.2 Build and run images by using ACR Tasks

ACR Tasks can build in Azure and can automate builds on source changes or base-image updates. A quick task needs only source context, a registry, and an image name.

~~~bash
az acr build \
  --registry myregistry \
  --image ai-api:v1 \
  .
~~~

The task uploads build context and performs the build in Azure; it does not require a local Docker daemon. Multi-step tasks support build, test, and push workflows.

**Question signals**

- “Build in the cloud,” “no local Docker,” or “base-image update trigger” → ACR Tasks.
- “Store and pull an existing image” → ACR repository operations, not necessarily a task.

### 1.1.3 Deploy containers to Azure App Service

App Service is a managed web-hosting choice. Configure the image source, startup/runtime behavior, environment settings, identity, ingress port, and diagnostics.

~~~bash
az webapp config container set \
  --resource-group rg-ai \
  --name app-ai-api \
  --container-image-name myregistry.azurecr.io/ai-api:v1 \
  --container-registry-url https://myregistry.azurecr.io

az webapp config appsettings set \
  --resource-group rg-ai \
  --name app-ai-api \
  --settings APP_ENV=Production FEATURE_VECTOR=true
~~~

For credential-free ACR pulls:

1. Enable a managed identity on the web app.
2. Assign the identity the ACR pull role.
3. Configure App Service to use managed-identity credentials for the registry.
4. Ensure the registry accepts ARM audience tokens as required by the documented setup.

App settings are injected into the container as environment variables. A setting is configuration; a secret belongs in Key Vault and should be accessed by identity or an appropriate reference pattern.

**When to use App Service:** A web site/API needs a managed web platform, built-in deployment/hosting features, and not Kubernetes primitives.

**Common mistakes**

- Supplying registry admin credentials when a managed identity can pull.
- Assuming the application listens on the expected port without configuring the documented container port behavior.
- Treating container filesystem persistence as durable application data.
- Changing an app setting but debugging the old process before restart/reload behavior has taken effect.

**Exam angle:** Expect a partial configuration and choose the missing identity, role, app setting, image reference, or logging step.

**Key facts to remember**

- ACR holds images; App Service runs them.
- Managed identity authenticates; ACR role assignment authorizes pull.
- App Service settings become container environment variables.
- Use immutable deployment references for rollback and traceability.

## 1.2 Implement container-orchestrated solutions

### What Microsoft expects

Deploy applications to Azure Container Apps, configure environments and revisions, scale with KEDA, deploy AKS workloads from manifests, and troubleshoot both platforms with logs, events, and connectivity checks.

### 1.2.1 Azure Container Apps: environments, apps, and revisions

An Azure Container Apps environment is the security and operational boundary for related apps and jobs. Apps in an environment can share a virtual network and logging destination. A revision is an immutable snapshot of an app version.

| Concept | Meaning | Exam decision |
|---|---|---|
| Environment | Boundary around apps/jobs and shared infrastructure | Co-locate related apps needing shared network/logging context |
| Revision | Immutable app-version snapshot | Create a new revision for revision-scope changes |
| Single mode | Traffic goes to the latest active revision | Straightforward rolling deployment |
| Multiple mode | Multiple revisions active with weights | Canary or A/B traffic |
| Labels | Stable, unique revision URLs | Test a revision without shifting production traffic |
| Secret | Application-scoped, outside a revision | Secret changes do not themselves create revisions |
| Environment variable | Revision-scope container setting | Updating it creates a new revision |

Changing a secret does not automatically update running revisions. Create a new revision or restart existing revisions so containers consume the new value. In production, Microsoft recommends Key Vault references rather than putting secret material directly in the Container Apps secret store.

~~~bash
az containerapp update \
  --name ai-api \
  --resource-group rg-ai \
  --image myregistry.azurecr.io/ai-api:v2 \
  --set-env-vars APP_ENV=Production API_KEY=secretref:api-key
~~~

### 1.2.2 Event-driven scaling with KEDA

Container Apps uses declarative scaling and KEDA-based event scalers. An HTTP app can scale by concurrent requests; a worker can scale from an external event source such as a Service Bus queue.

| Setting | Effect |
|---|---|
| Minimum replicas = 0 | Scale to zero is possible; cold-start latency can occur |
| Minimum replicas ≥ 1 | Keeps capacity ready and avoids scale-from-zero latency |
| Maximum replicas | Bounds horizontal scale |
| Polling interval / cooldown | Influences scale responsiveness and scale-in |
| Rule metadata | Defines the metric and threshold used by the selected scaler |
| Authentication reference | Lets the scaler access its event source without embedding credentials |

At the review baseline, Microsoft documents defaults of 0 minimum and 10 maximum replicas, with maximum configurable up to 1,000. Treat these as volatile and verify before the exam. Changing scaling rules creates a new revision.

**Question signals**

- Queue depth should drive worker count → KEDA event rule for the queue.
- Idle workload should cost no compute → minimum replicas 0, if cold starts are acceptable.
- Always-ready API → minimum at least 1.
- Safe release split → multiple revision mode and traffic weights.

### 1.2.3 Deploy and manage AKS workloads by manifest

AKS exposes Kubernetes application primitives. A typical deployment needs a Deployment for desired pods and a Service for stable discovery/traffic. ConfigMaps hold non-secret configuration; Kubernetes Secrets hold sensitive values, though Azure-integrated secret patterns can further reduce stored credentials.

~~~yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ai-worker
spec:
  replicas: 2
  selector:
    matchLabels:
      app: ai-worker
  template:
    metadata:
      labels:
        app: ai-worker
    spec:
      containers:
        - name: worker
          image: myregistry.azurecr.io/ai-worker:v3
          envFrom:
            - configMapRef:
                name: worker-config
---
apiVersion: v1
kind: Service
metadata:
  name: ai-worker
spec:
  selector:
    app: ai-worker
  ports:
    - port: 80
      targetPort: 8080
  type: ClusterIP
~~~

~~~bash
kubectl apply -f workload.yaml
kubectl rollout status deployment/ai-worker
kubectl get pods,services
~~~

Service choices:

| Service type | Reachability |
|---|---|
| ClusterIP | Internal cluster virtual IP; default |
| NodePort | Exposes a port on each node |
| LoadBalancer | Requests an external or internal Azure load balancer |
| ExternalName | DNS alias to an external name |

**When to use AKS:** Kubernetes APIs, manifests, cluster networking/policy, specialized scheduling, or cluster-level control are explicit requirements. Otherwise, Container Apps often removes control-plane work.

### 1.2.4 Monitor and troubleshoot AKS and Container Apps

Use a layered workflow:

1. **Desired state:** Is the correct image/revision/deployment active?
2. **Runtime state:** Are replicas scheduled, starting, ready, and healthy?
3. **Application output:** Inspect stdout/stderr and exceptions.
4. **Service discovery:** Check selectors, endpoints, DNS, and service/target ports.
5. **Network policy/path:** Test connectivity from the caller and verify ingress/egress rules.
6. **Dependencies:** Correlate downstream failures by distributed trace.

~~~bash
# AKS
kubectl get pods -o wide
kubectl describe pod POD_NAME
kubectl logs POD_NAME --previous
kubectl get events --sort-by=.lastTimestamp
kubectl get service,endpoints

# Container Apps
az containerapp logs show --name ai-api --resource-group rg-ai --follow
az containerapp env logs show --name ai-env --resource-group rg-ai --follow
~~~

Kubernetes events are retained for a limited period—Microsoft documents one hour by default in AKS unless collected by a monitoring solution. Container Apps distinguishes console logs from platform/system logs.

### Exam Trap

A running pod does not prove connectivity. A Service with a selector that does not match pod labels can have no endpoints. Check labels/selectors and endpoints before changing network infrastructure.

**Key facts to remember**

- Revision traffic controls release exposure; replicas control capacity.
- Secret changes do not create a revision; environment-variable and scale-rule changes do.
- KEDA chooses scale from an event metric; it does not process the message.
- AKS manifests declare workload state; <code>kubectl describe</code>, logs, events, Services, endpoints, and DNS explain failures.

# DOMAIN 2 — Develop AI solutions by using Azure data management services

**Weight: 25–30% — highest-priority domain**

## Vector concepts you need—no more, no less

An embedding is an array of numbers representing content. Similar items are expected to be near each other according to a chosen distance/similarity metric. The stored vector dimension and numeric type must match the embedding model output and index schema.

| Concept | Practical meaning |
|---|---|
| Exact search | Compares broadly enough to return exact nearest results; strongest recall, more compute |
| Approximate nearest neighbor (ANN) | Searches an optimized graph/index; lower latency or scale in exchange for possible recall loss |
| Cosine | Compares direction; common for normalized semantic embeddings |
| Dot product / inner product | Measures aligned magnitude/direction; model/index must match |
| Euclidean/L2 | Geometric distance |
| Metadata filter | Narrows candidates by tenant, category, date, ACL, or other fields |
| RAG retrieval | Retrieves relevant stored content before a generative model produces an answer |

**MUST KNOW:** The distance function configured on the index and used in the query must agree. Dimension and data type mismatches are configuration errors, not tuning issues.

## 2.1 Develop solutions that use Azure Cosmos DB for NoSQL

### What Microsoft expects

Connect with the SDK, issue efficient queries, tune RU consumption through partition-aware access and indexing, choose consistency deliberately, store/search embeddings, and implement change processing.

### 2.1.1 Connect with the SDK and run queries

Cosmos DB for NoSQL stores JSON items in containers. Each item has an <code>id</code> and a logical partition-key value. The partition key controls data placement and query routing, so it is an application design decision.

~~~python
from azure.cosmos import CosmosClient
from azure.identity import DefaultAzureCredential

credential = DefaultAzureCredential()
client = CosmosClient(COSMOS_ENDPOINT, credential=credential)
database = client.get_database_client("ai")
container = database.get_container_client("documents")

# Lowest-cost read shape when both identity values are known.
item = container.read_item(item="doc-42", partition_key="tenant-a")

query = """
SELECT TOP 10 c.id, c.title
FROM c
WHERE c.tenantId = @tenant AND c.status = @status
"""
rows = list(container.query_items(
    query=query,
    parameters=[
        {"name": "@tenant", "value": "tenant-a"},
        {"name": "@status", "value": "ready"},
    ],
    partition_key="tenant-a",
))
~~~

Use parameterized SQL queries. Supply the partition key when the query targets one logical partition. Cross-partition querying is valid when required but usually touches more partitions.

**Exam angle:** If both <code>id</code> and partition key are known, choose a point read rather than a SQL query. Microsoft documents that a 1-KB point read is roughly 1 RU.

### 2.1.2 Optimize query performance and RU consumption

A request unit (RU) normalizes CPU, I/O, and memory consumed by an operation. The same query over the same data consumes the same number of RUs. Relevant cost drivers include item size, indexed properties, query complexity, consistency, and partition fan-out.

Optimization order:

1. Use an <code>id</code> + partition-key point read when possible.
2. Route a query to one partition when the business lookup permits it.
3. Select only needed fields and bound result size.
4. Inspect request charge, query metrics, and index metrics.
5. Add a composite index for supported multi-property ordering/filter patterns.
6. Exclude unused paths if write RU and index storage matter.
7. Avoid expressions that force scans when a documented index-friendly alternative exists.

~~~python
items = container.query_items(
    query="SELECT * FROM c WHERE c.tenantId = @t",
    parameters=[{"name": "@t", "value": "tenant-a"}],
    partition_key="tenant-a",
    populate_query_metrics=True,
    populate_index_metrics=True,
)
list(items)
print(items.get_response_headers().get("x-ms-request-charge"))
~~~

The default indexing policy indexes every property and uses range indexes for strings and numbers. Consistent indexing updates synchronously with item writes. <code>None</code> disables indexing; use it only when query behavior permits. Composite indexes support queries such as <code>ORDER BY</code> across multiple properties.

### Consistency decisions

From strongest to weakest: **Strong → Bounded staleness → Session → Consistent prefix → Eventual**.

| Level | Requirement signal |
|---|---|
| Strong | Reads must return the latest committed version |
| Bounded staleness | Lag must be bounded by versions or time |
| Session | A client/session needs read-your-writes; default account consistency |
| Consistent prefix | Writes must never be observed out of order |
| Eventual | Lowest consistency guarantee is acceptable |

Strong and bounded-staleness reads consume approximately twice the RU of the relaxed levels. A client/request can relax consistency relative to the account default; it cannot request a stronger guarantee than the configured account supports.

### Exam Trap

Provisioning more throughput can reduce throttling but does not make an inefficient cross-partition query efficient. First inspect query shape, partition routing, and index utilization.

### 2.1.3 Embeddings and vector similarity search

Cosmos DB can co-locate vector embeddings with their source JSON and filter metadata in the same query.

The container vector policy defines:

- path to the vector;
- numeric data type;
- dimension count;
- distance function: cosine, dot product, or Euclidean.

The vector index chooses the search strategy:

| Cosmos index | Search | Documented constraints/use |
|---|---|---|
| <code>flat</code> | Exact | Up to 505 dimensions |
| <code>quantizedFlat</code> | Quantized brute-force | Up to 4,096 dimensions; useful for smaller filtered sets |
| <code>diskANN</code> | Approximate | Up to 4,096 dimensions; designed for larger sets |

Microsoft documents that <code>quantizedFlat</code> and <code>diskANN</code> use a full scan until at least 1,000 vectors exist. As a planning guideline, quantized flat is suited to scoped vector counts around 50,000 or below, while DiskANN is generally the large-set choice. Treat size guidance as workload-dependent, not an invariant cutoff.

~~~sql
SELECT TOP 5
    c.id,
    c.title,
    VectorDistance(c.embedding, @queryVector) AS distance
FROM c
WHERE c.tenantId = @tenant
ORDER BY VectorDistance(c.embedding, @queryVector)
~~~

Use <code>TOP N</code>. Add metadata filters, especially tenant or authorization boundaries, when the application requires them. The vector path cannot contain wildcards or arrays. The vector policy and vector-index configuration cannot be edited in place; remove and add the policy/index as documented.

**Configuration sequence**

1. Enable the vector-search feature at the account.
2. Create a container with matching vector policy and vector index.
3. Store vectors using the configured numeric type/dimension.
4. Query using <code>VectorDistance</code> with <code>TOP N</code>.
5. Inspect latency/RU/recall; for DiskANN, tune the search-list multiplier when the documented recall-cost tradeoff requires it.

### Exam Trap

An ANN index does not guarantee exact nearest-neighbor recall. If the requirement explicitly demands exactness and the vector dimension fits, examine the exact <code>flat</code> option and the cost implications.

### 2.1.4 Process changes

The change feed is a persistent ordered record of changes within each logical partition. The change feed processor (CFP) divides work among host instances using leases and provides at-least-once processing.

CFP components:

- **Monitored container:** source of changes.
- **Lease container:** ownership, continuation, and load-balancing state.
- **Host:** compute instance running the processor; each instance needs a unique instance name.
- **Delegate/handler:** application code processing batches.

All instances of one logical processor share the same processor name and lease container. Design the handler to be idempotent because a batch can be delivered again.

~~~csharp
ChangeFeedProcessor processor = source
    .GetChangeFeedProcessorBuilder<MyItem>(
        processorName: "embedding-indexer",
        onChangesDelegate: HandleChangesAsync)
    .WithInstanceName(Environment.MachineName)
    .WithLeaseContainer(leases)
    .Build();

await processor.StartAsync();
~~~

**Language boundary:** Microsoft documents the change feed processor for .NET SDK v3 and Java SDK v4. For Python and Node.js, use the pull model and manage checkpoints/continuations. Do not assume the Python SDK exposes the same CFP builder API.

By default a newly started processor begins from the current point rather than processing all historical items. Configure an appropriate start time; the documented beginning-of-time pattern is needed for full backfill.

**Preview:** All versions and deletes mode is documented as Preview. Latest-version mode covers creations and updates, not a full delete history.

**Exam angle:** For horizontally scaled consumers, use the lease container and unique host instance names. For correctness after retries, make writes idempotent.

**Key facts to remember**

- Point read: <code>id</code> + partition key.
- Partition fan-out and index mismatch are common RU causes.
- Session is the default consistency level.
- Cosmos vectors remain beside application data.
- CFP is at-least-once; leases coordinate hosts; idempotency is required.
- Python uses the pull model rather than the documented CFP builder.

### 2.2.1 Connect and query with the SDK/driver

Use a PostgreSQL driver such as Psycopg. Microsoft Entra authentication lets the application use a token rather than store a database password. TLS is required in the documented example.

### 2.2.2 Model schemas, indexes, tables, and data types

Model relational filters as typed columns, keep vector dimension explicit, and index according to the query.

~~~sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE documents (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id   text NOT NULL,
    category    text NOT NULL,
    content     text NOT NULL,
    embedding   vector(1536) NOT NULL,
    created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX ix_documents_tenant_category
    ON documents (tenant_id, category);
~~~

Relational indexes accelerate selective metadata predicates. A vector index accelerates nearest-neighbor ordering. They solve different parts of a hybrid query.

### 2.2.3 Balance indexing latency and pgvector compute overhead

Without a vector index, PostgreSQL performs exact nearest-neighbor search: perfect recall, but it scans and computes distance across the candidate set. Approximate indexes exchange some recall and build/storage cost for lower query latency.

| Index | Strength | Tradeoff |
|---|---|---|
| IVFFlat | Faster build, lower memory than HNSW | Requires training/data; speed–recall tuned with lists/probes |
| HNSW | Strong query speed/recall; can be built without training set | Slower build and more memory |
| DiskANN | Flexible Server extension designed for a latency/recall/memory balance | Azure-specific extension/configuration; ANN, not exact |

Load representative data before creating an IVFFlat index. The pgvector index operator class must match the query distance:

| Query operator | Distance | Example operator class |
|---|---|---|
| <code><-></code> | Euclidean/L2 | <code>vector_l2_ops</code> |
| <code><#></code> | Negative inner product | <code>vector_ip_ops</code> |
| <code><=></code> | Cosine | <code>vector_cosine_ops</code> |

~~~sql
CREATE INDEX ix_documents_embedding_hnsw
ON documents USING hnsw (embedding vector_cosine_ops);

SELECT id, content, embedding <=> $1 AS distance
FROM documents
WHERE tenant_id = $2 AND category = $3
ORDER BY embedding <=> $1
LIMIT 5;
~~~

Use <code>EXPLAIN (ANALYZE, VERBOSE, BUFFERS)</code> to verify the plan and actual work; do not infer index use from its existence.

Useful tuning controls:

- IVFFlat: <code>lists</code> affects index partitioning; <code>probes</code> trades latency for recall.
- HNSW: <code>m</code> and <code>ef_construction</code> affect graph/build; <code>ef_search</code> trades query work for recall.
- DiskANN: the documented search-list setting trades query work and latency for recall.

### 2.2.4 Select compute, memory, and storage

Azure Database for PostgreSQL Flexible Server provides Burstable, General Purpose, and Memory Optimized tiers. Vector workloads need enough memory for useful working sets/index operations and enough CPU for distance computation. Build operations can be memory and I/O intensive.

**Sizing workflow**

1. Establish vector count, dimension, filter selectivity, concurrency, and recall/latency target.
2. Observe CPU, memory pressure, storage latency/IOPS, connections, and query plans.
3. Tune schema/query/index before assuming scale is the only fix.
4. Choose General Purpose for balanced workloads; consider Memory Optimized when memory-to-vCore ratio is the limiting requirement.
5. Scale storage with care: Microsoft documents that storage can be increased but not reduced.

### 2.2.5 Similarity search and RAG with metadata filtering

RAG retrieval usually needs both semantic proximity and business constraints. Put tenant, ACL, status, language, or category predicates in the SQL query rather than retrieving globally and filtering only in application code.

Partial vector indexes or partitioning can help highly selective, stable filter patterns. Test actual plans: restrictive filters can change whether an ANN index is useful.

### 2.2.6 Optimize connections

Opening a database connection for every request wastes latency and server resources. Reuse connections through an application pool or the service’s PgBouncer capability where appropriate.

**Common mistakes**

- Using a global connection object without health checks or concurrency safety.
- Creating a pool so large that all app instances exhaust server connections.
- Reusing an expired Entra token for new connections.
- Expecting a B-tree metadata index to accelerate vector distance, or vice versa.
- Creating an operator-class index that does not match the query operator.

### Exam Trap

If query latency is high only under many concurrent app requests and server connection count spikes, connection pooling is more directly relevant than changing the vector distance function.

**Key facts to remember**

- PostgreSQL is the relational choice among the three in-scope data services.
- Exact scan maximizes recall; ANN indexes optimize speed/scale with recall tradeoffs.
- Metadata filtering is part of retrieval correctness, not just optimization.
- Use query plans and telemetry before resizing.
- Pool connections and refresh identity tokens.

## 2.3 Develop solutions that use Azure Managed Redis

### What Microsoft expects

Use Redis data operations, expiration and invalidation correctly, and create/query vector indexes for low-latency AI retrieval.

### 2.3.1 Data operations, cache expiration, and invalidation

Redis is an in-memory data platform. Common types include strings, hashes, and lists; counters are atomic. For caching, the cache-aside pattern is central:

1. Read from cache.
2. On miss, read the authoritative store.
3. Populate cache with a suitable expiration.
4. On an authoritative write, update the source first and invalidate the cached value.

~~~python
import json
import redis

r = redis.Redis(
    host=REDIS_HOST,
    port=10000,
    ssl=True,
    decode_responses=True,
)

def get_document(doc_id):
    key = f"doc:{doc_id}"
    cached = r.get(key)
    if cached:
        return json.loads(cached)

    value = load_from_authoritative_store(doc_id)
    r.set(key, json.dumps(value), ex=300)
    return value
~~~

Microsoft’s training documents port 10000 for Azure Managed Redis, in contrast with 6380 for Azure Cache for Redis. Use the correct product endpoint and current client guidance.

Expiration commands and results:

| Operation | Meaning |
|---|---|
| <code>SET ... EX seconds</code> / <code>SETEX</code> | Write with time-to-live |
| <code>EXPIRE</code> | Add/change TTL |
| <code>TTL</code> = positive | Remaining seconds |
| <code>TTL</code> = -1 | Key exists without expiry |
| <code>TTL</code> = -2 | Key does not exist |
| <code>PERSIST</code> | Remove expiration |

Use <code>SCAN</code> for incremental key iteration; do not use blocking <code>KEYS</code> in production workflows. Pipeline independent commands to reduce round trips. In a clustered deployment, multi-key operations need keys in the same hash slot or they can fail with <code>CROSSSLOT</code>.

**Cache correctness:** A cache is not the system of record. TTL limits staleness but does not guarantee consistency. Too short raises misses/source load; too long raises stale-data risk.

### 2.3.2 Vector indexing and similarity search

Azure Managed Redis vector search uses the RediSearch module. Enable it when provisioning; Microsoft documents that modules cannot be added later. Vector search is supported on Memory, Balanced, and Compute tiers, not Flash, and requires Enterprise clustering. Use the NoEviction policy for vector workloads as documented.

| Redis index | Behavior | Choose when |
|---|---|---|
| FLAT | Exact brute-force | Smaller set or exact recall requirement |
| HNSW | Approximate graph search | Larger set and low latency with recall tradeoff |

Supported documented distance metrics include L2, cosine, and inner product. Data can be stored in hashes or JSON. The declared vector type, dimensions, and metric must match the embedding.

~~~python
import numpy as np
from redis.commands.search.field import TagField, VectorField
from redis.commands.search.indexDefinition import IndexDefinition, IndexType
from redis.commands.search.query import Query

schema = (
    TagField("tenant"),
    VectorField(
        "embedding",
        "HNSW",
        {
            "TYPE": "FLOAT32",
            "DIM": 1536,
            "DISTANCE_METRIC": "COSINE",
        },
    ),
)

r.ft("idx:docs").create_index(
    schema,
    definition=IndexDefinition(prefix=["doc:"], index_type=IndexType.HASH),
)

query_bytes = np.asarray(query_vector, dtype=np.float32).tobytes()
query = (
    Query("(@tenant:{tenant_a})=>[KNN 5 @embedding $vec AS score]")
    .sort_by("score")
    .return_fields("score")
    .dialect(2)
)
result = r.ft("idx:docs").search(
    query,
    query_params={"vec": query_bytes},
)
~~~

**When to use Managed Redis vectors:** Very low-latency in-memory retrieval, semantic caching, or vector lookup close to an existing Redis access pattern. Re-evaluate if the authoritative data and relational/document semantics dominate more than cache latency.

### Exam Trap

Do not choose Redis merely because it supports vector search. If the scenario requires durable relational joins or partitioned JSON as the primary data model, PostgreSQL or Cosmos DB is the more direct fit; Redis can still complement them as a cache.

**Key facts to remember**

- Cache-aside: miss → source → fill; source write → invalidate.
- TTL is a staleness/cost tool, not a transaction guarantee.
- RediSearch must be enabled at creation.
- FLAT is exact; HNSW is approximate.
- Vector type, dimension, and metric must agree with the embedding.

## 3.1 Implement event- and message-based solutions

### What Microsoft expects

Select and implement Service Bus queues/topics and Event Grid subscriptions/custom events, including filters, retries, settlement, and failure handling.

### Event versus message

| Dimension | Event Grid event | Service Bus message |
|---|---|---|
| Meaning | A fact that happened | Work/data sent for a consumer to process |
| Typical routing | Fan-out notification to interested handlers | Queue or topic/subscription broker |
| Consumer expectation | React to notification; fetch more state if needed | Process command/business payload |
| Reliability controls | Subscription retry and dead-letter configuration | Locks, settlement, delivery count, DLQ, sessions/duplicate detection where configured |
| Typical signal | “Notify many systems when a resource changes” | “Process each job durably; failures must be isolated” |

Both are asynchronous and can be delivered more than once. Make handlers idempotent.

### 3.1.1 Service Bus queues, topics, subscriptions, and DLQs

- A **queue** has competing consumers: each message is processed by one receiver.
- A **topic** fans a copy to each matching subscription.
- A **subscription** behaves like a virtual queue and can filter the topic stream.
- SQL and correlation filters select messages for subscriptions.

Message structure includes a body, application properties, and broker-defined system properties. Use message ID for business identity/duplicate handling, correlation ID for workflow correlation, content type for interpretation, and application properties for routing/filtering. For large payloads, store the payload externally and send a reference—the claim-check pattern.

~~~python
from azure.identity import DefaultAzureCredential
from azure.servicebus import ServiceBusClient, ServiceBusMessage

credential = DefaultAzureCredential()
with ServiceBusClient(SERVICE_BUS_FQDN, credential) as client:
    with client.get_queue_sender("embedding-jobs") as sender:
        sender.send_messages(ServiceBusMessage(
            '{"documentId":"doc-42"}',
            message_id="embed-doc-42-v7",
            correlation_id="ingestion-901",
            application_properties={"tenant": "tenant-a"},
        ))
~~~

#### Receive modes and settlement

| Behavior | Result | Use |
|---|---|---|
| PeekLock | At-least-once; receiver settles after processing | Default for reliable work |
| ReceiveAndDelete | Removed when delivered; at-most-once | Loss is acceptable and speed matters |
| Complete | Successful processing; remove message | Success path |
| Abandon | Release for redelivery | Transient failure |
| Dead-letter | Move to DLQ with reason | Permanent/invalid message |
| Defer | Keep aside and retrieve later by sequence number | Processing order/dependency requires postponement |

~~~python
with client.get_queue_receiver(
    queue_name="embedding-jobs",
    max_wait_time=5,
) as receiver:
    for message in receiver:
        try:
            process(str(message))
            receiver.complete_message(message)
        except InvalidPayload as exc:
            receiver.dead_letter_message(
                message,
                reason="InvalidPayload",
                error_description=str(exc),
            )
        except TransientDependencyError:
            receiver.abandon_message(message)
~~~

Microsoft documents a default maximum delivery count of 10. When exceeded, the broker moves the message to the DLQ. The DLQ has no automatic cleanup and TTL is not observed while a message is in it; build an operational receiver/remediation process. You cannot dead-letter a message from the DLQ into another subqueue.

Duplicate detection can suppress a resent message with the same ID during the configured window, but it does not replace idempotent business processing.

**Question signals**

- One work item, one competing worker → queue.
- Independent consumer groups each need a copy → topic plus subscriptions.
- Poison messages must stop blocking the main path → DLQ plus monitoring/remediation.
- Do not lose a delivered message if a worker crashes → PeekLock, then complete only after success.

### Exam Trap

Calling <code>Complete</code> before the side effect finishes can lose work. Completing after the side effect creates a possible replay window, so the side effect must be idempotent.

### 3.1.2 Event Grid filters, custom events, and retries

For new custom integrations, Microsoft recommends the CloudEvents 1.0 schema. A CloudEvent includes fields such as <code>specversion</code>, <code>type</code>, <code>source</code>, and <code>id</code>, with optional <code>subject</code>, <code>time</code>, <code>datacontenttype</code>, and <code>data</code>.

Filters can use:

- event type;
- subject prefix/suffix;
- advanced operators against event fields.

Put stable routing attributes in filterable fields. The event should state a fact and normally carry only the data needed by handlers; link to large results rather than embedding them.

~~~python
from azure.core.messaging import CloudEvent
from azure.eventgrid import EventGridPublisherClient
from azure.identity import DefaultAzureCredential

publisher = EventGridPublisherClient(
    EVENT_GRID_ENDPOINT,
    DefaultAzureCredential(),

        subject="tenants/tenant-a/documents/doc-42",

    )
])
~~~

The publishing identity needs the Event Grid data-sender role. A subscription endpoint must acknowledge delivery successfully. Event Grid provides at-least-once delivery, retries according to the selected tier/resource’s documented policy, does not guarantee event ordering, and can dead-letter undeliverable events when configured.

**Important:** Event Grid basic topics and Event Grid namespaces can have different retry details. Do not transfer an exact retry schedule or limit from one model to the other; read the page for the resource named in the scenario.

**How to choose**

- Resource state changed; loosely coupled systems must react → Event Grid.
- Business work must be locked, settled, retried, or inspected in a broker queue → Service Bus.
- Many subscribers need tailored subsets of business messages → Service Bus topic filters.
- Subscribers need filtering by event type/subject/data → Event Grid subscription filters.

~~~python
import azure.functions as func

        status_code=200,

@app.service_bus_queue_trigger(
    arg_name="message",
    queue_name="embedding-jobs",
    connection="ServiceBusConnection",
)
def index_document(message: func.ServiceBusMessage) -> None:
    process_job(message.get_body().decode("utf-8"))
~~~

## 4.1 Secure Azure solutions

### What Microsoft expects

Retrieve and rotate secrets with Key Vault and centralize application settings in App Configuration, using identity and authorization correctly.

### 4.1.1 Identity, roles, secrets, and configuration

Keep four concerns separate:

| Concern | Question | Azure mechanism |
|---|---|---|
| Authentication | Who is the caller? | Microsoft Entra token; managed/workload identity |
| Authorization | What may it do? | Azure RBAC/data-plane role or database grant |

### 4.1.2 Retrieve and rotate Key Vault secrets

~~~python
from azure.identity import DefaultAzureCredential
from azure.keyvault.secrets import SecretClient

credential = DefaultAzureCredential()
secrets = SecretClient(
    vault_url=KEY_VAULT_URI,
    credential=credential,
~~~

1. Create a new secret version.
2. Update or refresh consumers.
3. Verify the new credential.
4. Disable/retire the old version according to the system’s rotation procedure.
5. Monitor failures and expiration.

### 4.1.3 Store and retrieve configuration with App Configuration

~~~python
from azure.appconfiguration.provider import load, SettingSelector, WatchKey
from azure.identity import DefaultAzureCredential

credential = DefaultAzureCredential()
config = load(
    endpoint=APP_CONFIG_ENDPOINT,
    credential=credential,
    selects=[
        SettingSelector(key_filter="AI:*", label_filter="Production"),
    ],
    refresh_on=[
        WatchKey("AI:Sentinel", label="Production"),
    ],
)
model_name = config["AI:ModelName"]
~~~

The Python provider caches configuration. Refresh is activity-driven and rate-limited; a failed refresh can continue using cached configuration. Microsoft documents a default refresh interval of 30 seconds. A sentinel key lets an application refresh a group of settings only after all related updates are complete.

Feature flags are not loaded by default and have their own refresh configuration. For Key Vault references, give the identity App Configuration data-reader access and Key Vault secret access; the provider resolves the referenced URI.

**When to use what**

- Endpoint, model deployment name, threshold, or feature switch → App Configuration.
- Password, signing key, API key, or certificate → Key Vault.
- App Configuration value needs a secret → store a Key Vault reference, not secret plaintext.
- Azure service supports Entra identity → prefer identity over a stored connection secret.

**Common mistakes**

- Storing a secret as a plain App Configuration value.
- Assuming a Key Vault reference grants Key Vault access.
- Changing several related keys without a sentinel/version strategy, allowing mixed configuration.
- Expecting time alone to refresh an inactive application; refresh is triggered by application activity.

## 4.2 Monitor and troubleshoot Azure solutions

### What Microsoft expects

Instrument distributed calls with OpenTelemetry, analyze logs and metrics with KQL, and correlate requests, dependencies, traces, and exceptions to isolate failures.

### 4.2.1 Signal → tool → diagnosis → action

| Signal | Best for | Example diagnosis |
|---|---|---|
| Metric | Numeric trend, threshold, aggregation, alert | p95 latency increased when replica count reached maximum |
| Log | Detailed discrete record and ad hoc correlation | Exceptions for one tenant or revision |
| Trace | End-to-end causal flow and latency attribution | API is fast until PostgreSQL dependency span |
| Kubernetes/ACA platform event | Scheduling, image pull, health, revision, system state | Pod pending or container image pull failed |

Metrics tell you **that** behavior changed. Logs tell you **what records** were emitted. Traces tell you **where a distributed request spent time or failed**.

### 4.2.2 Instrument distributed tracing with OpenTelemetry

Microsoft recommends the Azure Monitor OpenTelemetry Distro for supported scenarios. Configure it once, set a meaningful service name, and propagate trace context across HTTP and messaging boundaries.

~~~python
from azure.monitor.opentelemetry import configure_azure_monitor
from opentelemetry import trace

configure_azure_monitor()
tracer = trace.get_tracer(__name__)

def retrieve_context(tenant_id, query_vector):
    with tracer.start_as_current_span("vector.retrieve") as span:
        span.set_attribute("app.tenant", tenant_id)
        span.set_attribute("db.system", "postgresql")
        return run_vector_query(tenant_id, query_vector)
~~~

The distro automatically instruments supported libraries such as <code>requests</code>, Flask/Django/FastAPI, Psycopg2, Azure SDKs, and Python logging. Custom spans should represent meaningful application operations and carry useful, non-sensitive attributes.

Resource attributes describe the service/resource; span attributes describe one operation. Configure <code>service.name</code> so Application Map and correlated telemetry identify components meaningfully. Record exceptions and status without putting secrets, full prompts, tokens, or personal data into telemetry.

Application Insights maps telemetry concepts:

- incoming server/consumer work → requests;
- outgoing client/producer calls → dependencies;
- diagnostic events → traces;
- failures → exceptions.

All telemetry for one distributed operation shares <code>operation_Id</code> when propagation works.

### 4.2.3 Analyze logs and metrics with KQL

KQL is a pipeline: start with a table, filter rows, shape/project fields, aggregate, sort, and render.

Application Insights resource scope uses tables such as <code>requests</code>, <code>dependencies</code>, <code>traces</code>, and <code>exceptions</code>. Workspace-based schemas use names such as <code>AppRequests</code>, <code>AppDependencies</code>, and <code>AppExceptions</code>. Match the query to the selected scope.

~~~kusto
// Failed requests by operation
requests
| where timestamp > ago(1h)
| where success == false
| summarize failures=count() by operation_Name
| order by failures desc
~~~

~~~kusto
// Slow dependencies and their target
dependencies
| where timestamp > ago(1h)
| where duration > 1s
| summarize calls=count(), p95=percentile(duration, 95)
    by target, type, name
| order by p95 desc
~~~

~~~kusto
// Correlate one failed request across telemetry
let failedOperation =
    toscalar(
        requests
        | where success == false
        | top 1 by timestamp desc
        | project operation_Id
    );
union requests, dependencies, traces, exceptions
| where operation_Id == failedOperation
| order by timestamp asc
~~~

Prefer <code>where</code> early to reduce data, then <code>project</code> needed columns and <code>summarize</code> only at the required dimension. Use <code>bin(timestamp, 5m)</code> for time series.

### Troubleshooting workflow

1. Define symptom, time window, impacted operation, and deployment/revision.
2. Check high-level rate, failure, duration, and saturation metrics.
3. Select a failed or slow request.
4. Follow its operation/trace through dependencies and exceptions.
5. Inspect component logs/platform events at the failure timestamp.
6. Test the smallest hypothesis: identity/role, DNS/port, pool exhaustion, throttling, bad revision, stale configuration, or poison message.
7. Fix, redeploy/configure safely, and verify the same telemetry query.

### Exam Trap

Searching each service’s logs by message text may miss the cross-service cause. If the scenario provides a trace or operation identifier, correlate on that identifier first.

**Key facts to remember**

- OpenTelemetry creates and propagates trace context; Azure Monitor/Application Insights stores and analyzes exported telemetry.
- Requests and dependencies should share an operation ID.
- Use metrics for trend/alert, logs for detailed events, traces for causality.
- KQL table names differ by resource versus workspace schema.

| Requirement | Preferred Azure capability | Why | Alternative / why not |
|---|---|---|---|
| Managed web/API container without Kubernetes administration | App Service custom container | Managed web-hosting model and container deployment | Container Apps if revision/event-scale model matters; AKS if Kubernetes control is required |
| Revisioned microservice with traffic splitting and scale-to-zero | Azure Container Apps | Revisions, labels/weights, KEDA scaling | App Service lacks the same revision model; AKS adds cluster operations |
| Kubernetes manifests, cluster networking/policy, specialized scheduling | AKS | Exposes Kubernetes control and primitives | Container Apps abstracts the cluster |
| Trigger-oriented bursty code | Azure Functions | Native triggers/bindings and serverless scaling | Container worker if process/runtime packaging drives design |
| Private Azure image registry and cloud builds | ACR + ACR Tasks | Artifact management plus registry-side build | Runtime hosts consume images; they do not replace the registry |
| JSON documents, global partitioning, item + vector co-location | Cosmos DB for NoSQL | Partitioned NoSQL API and integrated vector search | PostgreSQL if joins/relational constraints dominate |
| SQL, joins, typed relational schema, and vector retrieval | Azure Database for PostgreSQL | Relational semantics plus pgvector/DiskANN choices | Cosmos DB if document partition model dominates |
| In-memory cache or semantic cache with vector retrieval | Azure Managed Redis | Cache data types, TTL, low-latency vector index | Not the automatic choice for authoritative relational/document storage |
| Durable command processed by one worker | Service Bus queue | Lock, settlement, retry, DLQ | Event Grid is notification-oriented |
| Business message copied to independent consumers | Service Bus topic/subscriptions | Durable brokered pub/sub and subscription filters | Event Grid if the payload is an event fact and push notification fits |
| Notify handlers that a resource/fact changed | Event Grid | Event routing, filters, retry/dead-letter configuration | Service Bus if work ownership and settlement are required |
| Store an API key or certificate | Key Vault | Purpose-built secret/certificate/key service | App Configuration should hold settings or a Key Vault reference |
| Centralize labeled settings and feature flags | App Configuration | Key-values, labels, refresh, feature management | Key Vault is for confidential material, not general settings |
| Find the slow dependency in a multi-service request | OpenTelemetry trace + Application Insights | Context-correlated request/dependency spans | Aggregate metrics show trend, not causal path |
| Alert on a rising failure rate | Azure Monitor metric/log alert | Aggregation over time and thresholding | One trace is evidence for diagnosis, not the trend itself |

# EXAM TRAPS

1. **Tag ≠ immutable image.** A moving tag can hide what was deployed; a digest identifies content.
2. **Authentication ≠ authorization.** Managed identity still needs an appropriate role/grant.
3. **Container Apps secret update ≠ revision update.** Restart or create a new revision so the process sees the new value.
4. **KEDA scales; it does not process.** The worker and its message correctness still matter.
5. **Healthy pod ≠ reachable service.** Check labels, selectors, endpoints, target port, DNS, then policy.
6. **More RUs ≠ optimized Cosmos query.** Point reads, partition routing, and indexing come first.
7. **Session consistency ≠ global strong consistency.** It supplies session-scoped read-your-writes.
8. **Vector index exists ≠ query uses it.** Metric/operator class, query shape, population, and plan matter.
9. **ANN ≠ exact.** HNSW/DiskANN/IVFFlat introduce recall tradeoffs.
10. **Cache TTL ≠ consistency guarantee.** Invalidate after authoritative writes and tolerate cache failure/staleness.
11. **Duplicate detection ≠ idempotency.** Replays can still happen outside its conditions/window or after side effects.
12. **Abandon ≠ dead-letter.** Abandon retries; dead-letter isolates a message for investigation.
13. **Event ≠ command.** “Something happened” points to Event Grid; “perform this durable work” points to Service Bus.
14. **Long function timeout ≠ long HTTP response.** The documented load-balancer response limit still applies.
15. **Key Vault reference ≠ secret permission.** The application must be authorized to resolve the referenced vault value.
16. **A metric ≠ a distributed trace.** Use trace correlation to attribute dependency latency.
17. **Application Insights table names are scope-sensitive.** Resource scope and workspace schema names differ.
18. **Preview ≠ GA.** Cosmos change feed “all versions and deletes” is Preview; label it and verify support.

# SCENARIO PATTERNS

## Pattern 1 — Queue-driven embedding workers

**Requirements**

- API must respond quickly.
- Each document requires durable background processing.
- Workers can scale to zero.
- Poison inputs require inspection.

**Important clues** → durable work, asynchronous response, queue length, DLQ.

**Eliminate** → Event Grid alone, because explicit work ownership/settlement is required; always-on AKS if no Kubernetes constraint exists.

**Best choice** → API publishes a Service Bus queue message; a Container Apps worker uses a Service Bus KEDA rule with minimum replicas 0, processes under PeekLock, completes after idempotent success, and monitors DLQ depth.

## Pattern 2 — Tenant-aware document RAG

**Requirements**

- JSON documents and embeddings stay together.
- Queries always include tenant partition.
- Scale is global; operational cost is measured in RUs.

**Important clues** → partitioned JSON, RU, integrated vector distance, tenant filter.

**Best choice** → Cosmos DB for NoSQL with a tenant-aware partition key, vector policy/index, <code>TOP N</code> vector query plus tenant predicate, and request/index metrics.

## Pattern 3 — Relational RAG with rich metadata

**Requirements**

- Joins and relational constraints are required.
- Similarity query filters by ACL/category.
- The team can trade recall for latency.

**Best choice** → Azure Database for PostgreSQL with relational indexes plus a pgvector ANN index whose operator class matches the distance operator. Validate with <code>EXPLAIN ANALYZE</code>.

## Pattern 4 — Semantic cache

**Requirements**

- Repeated semantically similar prompts should be served at low latency.
- The durable database remains authoritative.
- Stale entries must age out and be invalidated on updates.

**Best choice** → Azure Managed Redis with RediSearch vector index, explicit TTL, and source-write-then-cache-invalidation. Redis is the acceleration layer, not the system of record.

## Pattern 5 — Safe container rollout

**Requirements**

- New image receives 5% traffic.
- Testers need a stable URL to the new version.
- Rollback must be quick.

**Best choice** → Container Apps multiple-revision mode, traffic weights, and a revision label. Use a unique image tag/digest.

## Pattern 6 — Secretless service access

**Requirements**

- Code and configuration must not store credentials.
- A container reads App Configuration and a Key Vault-backed secret.

**Best choice** → managed identity, App Configuration data-reader role, Key Vault secret data-plane role, <code>DefaultAzureCredential</code>, and an App Configuration Key Vault reference.

## Pattern 7 — Find a slow downstream dependency

**Requirements**

- API, function, and database each log separately.
- Only some requests are slow.
- Need the responsible downstream call.

**Best choice** → OpenTelemetry context propagation and Application Insights end-to-end transaction view/KQL correlation by <code>operation_Id</code>. Use dependency span duration.

## Pattern 8 — Resource-change fan-out

**Requirements**

- An event records that indexing completed.
- Several loosely coupled subscribers need different event types/subjects.
- No consumer owns a command lock.

**Best choice** → Event Grid CloudEvents and subscription filters. Configure retry/dead-letter behavior for the exact Event Grid resource model.

# SECURITY CHEAT SHEET

1. Prefer managed identity/workload identity where the target service supports Entra authentication.
2. Use <code>DefaultAzureCredential</code> as a credential chain; verify which identity actually wins in each environment.
3. Grant least-privileged **data-plane** access at the narrowest practical scope.
4. Store confidential values in Key Vault, not source code, image layers, plain environment files, logs, or plain App Configuration values.
5. Store non-secret settings/feature flags in App Configuration; a Key Vault reference is a URI and still requires vault permission.
6. Use TLS and documented secure endpoints.
7. Rotate unavoidable secrets with overlapping versions and verified consumer refresh.
8. Keep tenant/authorization filters in the retrieval path; vector similarity alone is not authorization.
9. Do not record credentials, tokens, sensitive prompts, or personal data as span attributes/log fields.
10. Treat authentication, authorization, configuration, and secret retrieval as separate failure points.

# Mixed Exam Review

Try to answer before expanding the key.

## Scenario A — Secure asynchronous ingestion

An HTTP Function accepts document IDs. Processing takes several minutes, must survive worker restarts, and should scale Container Apps workers to zero. Neither component may store broker credentials. What is the flow and which permissions are needed?

<details>
<summary>Reasoning</summary>

Return HTTP 202 after sending a Service Bus queue message. A Container Apps worker scales from the queue through a KEDA rule, receives with PeekLock, processes idempotently, and completes only after success. Give the Function identity send permission and the worker identity receive permission; configure the scaler’s documented identity-based access. Monitor queue age/depth and the DLQ.

</details>

## Scenario B — Retrieval architecture

The source is normalized business data with foreign keys and joins. Retrieval must filter by tenant and access group before ranking a 1,536-dimension cosine embedding. Which data platform and two index categories fit?

<details>
<summary>Reasoning</summary>

Use Azure Database for PostgreSQL. Create relational indexes for tenant/access predicates and a pgvector HNSW/other suitable vector index using <code>vector_cosine_ops</code>. Query with the matching cosine operator and inspect <code>EXPLAIN ANALYZE</code>. The exact ANN choice depends on measured build, memory, latency, and recall requirements.

</details>

## Scenario C — Configuration rotation failure

A Container App resolves a Key Vault reference through App Configuration. A new vault secret version exists, but the process still sees an old value. What layers do you inspect?

<details>
<summary>Reasoning</summary>

Verify the app identity and both data-plane roles, the Key Vault reference URI/version behavior, provider secret-refresh configuration, App Configuration refresh activity/interval, selected label, and the running revision/process. A direct Container Apps secret update also requires restart or a new revision to reach existing processes.

</details>

## Scenario D — Duplicate downstream writes

A Service Bus message shows multiple deliveries and a PostgreSQL row was inserted twice. The receiver uses PeekLock and completes after insertion. What is the durable fix?

<details>
<summary>Reasoning</summary>

At-least-once delivery allows replay between the database side effect and settlement. Make the operation idempotent—for example enforce a business/message ID uniqueness rule and treat an existing result as success—then complete. Duplicate detection can help with duplicate sends but is not a substitute for idempotent processing.

</details>

## Scenario E — “The database is slow”

API p95 rose after a release. Database CPU is normal, but some traces show long gaps before a database dependency and app instances report connection waits. What should be fixed first?

<details>
<summary>Reasoning</summary>

The trace and connection evidence point to pool exhaustion or connection churn before database execution. Inspect pool size per replica, total server connections, token renewal, and PgBouncer. Do not change vector indexes without plan/CPU/I/O evidence.

</details>

## Scenario F — Event-driven observability

An Event Grid custom event starts a Function that sends a Service Bus message to a worker. How do you make a single business operation diagnosable?

<details>
<summary>Reasoning</summary>

Use stable event/message IDs and correlation IDs, propagate OpenTelemetry trace context where supported by the producer/consumer instrumentation, name services, create consumer/producer spans, and query requests/dependencies/traces/exceptions by operation ID. Include useful non-sensitive routing identifiers, not secrets or full sensitive content.

</details>

# Final 60-Minute Review

## Minutes 60–45 — Service selection

- **App Service:** managed web/API container.
- **Container Apps:** managed revisions, traffic weights/labels, KEDA, scale-to-zero.
- **AKS:** Kubernetes manifests and cluster-level control.
- **Functions:** one trigger per function; bindings for inputs/outputs; choose plan by scale/network/deployment behavior.
- **Cosmos DB:** partitioned JSON, point reads, RUs, integrated vectors, change feed.
- **PostgreSQL:** relational schema/SQL/joins plus vector extensions and connection pooling.
- **Managed Redis:** in-memory cache/semantic cache, TTL, FLAT/HNSW vector search.
- **Service Bus:** durable commands/work, PeekLock settlement, DLQ.
- **Event Grid:** event facts, subscription filtering, fan-out, retry/dead-letter.
- **Key Vault:** secrets. **App Configuration:** settings, labels, feature flags, Key Vault references.

## Minutes 45–30 — Data and vectors

- Point read uses Cosmos <code>id</code> + partition key; avoid fan-out when possible.
- Inspect RU charge, query metrics, and index metrics before scaling throughput.
- Cosmos consistency: Strong → Bounded staleness → Session → Consistent prefix → Eventual; Session is default.
- Cosmos vector: <code>flat</code> exact/max 505 dimensions; <code>quantizedFlat</code> and <code>diskANN</code> max 4,096; DiskANN is the large-set ANN choice.
- Change feed processing is at-least-once. Leases coordinate hosts; unique instance names; idempotent handler. Python uses pull model.
- PostgreSQL: relational index for filters, vector index for distance. Match <code><-></code>/<code><#></code>/<code><=></code> to L2/IP/cosine operator class.
- Exact scan gives recall at compute cost. IVFFlat builds lighter; HNSW uses more build memory; DiskANN is Azure Flexible Server’s ANN option.
- Use <code>EXPLAIN (ANALYZE, BUFFERS)</code>; observe CPU, memory, I/O, and connections.
- Redis cache-aside: miss → source → fill; write source → invalidate cache. TTL does not guarantee consistency.
- Redis vector module is provision-time; Enterprise clustering and supported tier; FLAT exact, HNSW approximate.

## Minutes 30–20 — Containers and integration

- ACR: unique tag/digest. ACR Task: cloud build and triggers.
- ACA environment is a boundary; revision is an immutable version; scale-rule/env changes create revision; secret change does not.
- Minimum replicas 0 enables zero; ≥1 keeps readiness. KEDA metric drives replicas.
- AKS no endpoints → selector/labels; then ports, DNS, policy. Events are short-lived unless collected.
- Queue = competing consumers. Topic/subscriptions = copies to independent groups.
- PeekLock: complete success, abandon transient, dead-letter permanent, defer for later sequence retrieval.
- DLQ is not auto-cleaned; inspect reason and remediate.
- Event Grid: CloudEvents recommended for new work; filter by type/subject/advanced fields; no general ordering guarantee.
- HTTP Function work exceeding response limit → async queue + 202/status.

## Minutes 20–10 — Security

- Managed identity removes stored credentials only where the target accepts Entra tokens.
- <code>DefaultAzureCredential</code> authenticates; RBAC/data grants authorize.
- Key Vault secret access and App Configuration data access are separate permissions.
- A Key Vault reference stores a URI, not secret plaintext, and grants no vault access.
- App Configuration refresh is activity-driven/cached; sentinel updated last coordinates related values.
- Never put secrets in code, image layers, plain config values, logs, or trace attributes.

## Minutes 10–0 — Monitoring and traps

- Metric = trend/alert; log = detailed record; trace = causal path.
- Propagate context and correlate by <code>operation_Id</code>.
- Resource-scope tables: <code>requests</code>/<code>dependencies</code>; workspace: <code>AppRequests</code>/<code>AppDependencies</code>.
- Retry implies duplicate possibility; build idempotency.
- ANN implies recall tradeoff; an existing index may still not match the query.
- Authentication success can still yield authorization failure.
- Recheck exact limits/defaults before exam day.

# Final 20-Minute Review

1. Match compute: web container → App Service; revisions/KEDA → Container Apps; Kubernetes control → AKS; trigger/binding → Functions.
2. Match data: JSON/partition/RU → Cosmos; relational SQL/joins → PostgreSQL; cache/TTL/in-memory → Managed Redis.
3. Match integration: durable work → Service Bus; event fact/fan-out notification → Event Grid.
4. Match security: secret → Key Vault; non-secret setting/flag → App Configuration; identity plus role, never one without the other.
5. Match telemetry: trend → metric; record → log; cross-service cause → trace.
6. Cosmos: point read; partition-aware query; Session default; index only useful paths; <code>TOP N VectorDistance</code>; CFP is at-least-once.
7. PostgreSQL: metadata and vector indexes solve different predicates; distance operator must match operator class; pool connections.
8. Redis: source remains authoritative; invalidate after write; vector module at provisioning; FLAT exact/HNSW ANN.
9. ACA: revision traffic ≠ replicas; secret change ≠ revision; minimum 0 enables scale-to-zero.
10. Service Bus: PeekLock and settle after idempotent success; DLQ needs a consumer.
11. Event Grid: filter subscription, acknowledge delivery, do not assume ordering.
12. Function: one trigger; settings are environment-specific; long HTTP work becomes asynchronous.

- Do not memorize ANN tuning values without understanding the recall/latency/build-memory tradeoff.
- Do not memorize portal click paths. Understand what setting changes revision, identity, access, scale, routing, or data behavior.
- Do not memorize product marketing. Select by explicit workload semantics.
